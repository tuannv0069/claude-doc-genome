# Planning work and checking its result

## §1 Establish the outcome

Before changing an artifact or producing a deliverable, identify the result requested, its governing sources and where it belongs. A question that needs no changed artifact does not require a separate plan. When a skill owns the workflow, follow that procedure while preserving the evidence and authority requirements in this guide.

An accepted instruction to implement authorizes the ordinary implementation work. A plan is not another permission checkpoint. Ask only for a materially unresolved decision or an action outside existing authority, and continue independent work while that decision remains open.

## §2 Match preparation to consequence

For an isolated reversible edit, the plan can remain in the current working context: establish the intended change, make it and check it against the source. For dependent work across files or phases, save targets, ownership, dependencies, acceptance conditions and verification in the task workspace before execution.

Shared contracts, migration, broad reuse and costly irreversible operations warrant fuller preparation and independent plan review. Investigate uncertain risk instead of automatically imposing the largest process. Artifact type and planning depth are separate choices: writing does not require software tests merely because it changes a file.

## §3 Define evidence before execution

For each important outcome, identify what could show it wrong and how that evidence will be obtained. Use source evidence for investigations, applicable requirements for designs, execution checks for runtime claims and before-and-after comparison for migrations. A domain judgment needs the relevant evaluator and reasons; an easy count cannot substitute for whether a document or creative work serves its purpose.

### §3.6 Verify independently

For work beyond a small isolated change, obtain an independent agent or human comparison against the requirements and source material. Independent plan review does not replace review of the completed result. If required independence is unavailable, identify that limit instead of relabeling the author's self-check.

## §4 Make assignments executable

Split work into results that can be evaluated independently. Each assignment supplies exact targets, changes permitted, inputs, outputs, dependencies, required source paths and acceptance checks. Specify the behavior behind vague duties such as error handling. A dependency on another assignment is ready only when its required output is actually available.

Select the role and lesson stores for the delegated action, not simply the coordinator's role. Pass their paths and the target root. File count alone does not determine either a useful boundary or the reasoning capability required.

## §5 Execute with return paths

Compare the plan with every requested outcome before starting dependent work. Resolve missing producers, conflicting interfaces and acceptance conditions that lack evidence. Execute the authorized steps, inspect their actual results and update the saved state when new evidence changes the approach.

Return to the relevant earlier decision when an assumption fails. Stop only the dependent action when it becomes infeasible or exceeds authority; preserve progress on independent work. Before handoff, compare the final artifact with its sources and state what the checks actually establish.

## §6 Evaluate alternatives when a choice remains

Read the existing artifact and constraints before proposing another design. Compare viable alternatives when they change a material consequence or maintenance responsibility. Do not invent options merely to fill a fixed template, or ask the user to decide a choice already delegated. Record qualifying reasons under `decision-journal.md` §1.
